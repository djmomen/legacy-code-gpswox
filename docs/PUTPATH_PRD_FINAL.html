1. Overview

PutPath is an Agentic Fleet Operating System and AI Operations Workforce Platform for telematics, logistics, fleet, construction, and heavy-equipment companies. A multi-customer SaaS (GPSWOX-style account model) — not a framework, not a single-customer deployment.

PutPath is the AI operating layer that turns fleet data, documents, alerts, and workflows into assigned work, investigations, reports, approvals, and operational decisions.

It is NOT a GPS dashboard, reporting tool, chatbot, or Traccar wrapper. Operational Intelligence Loop (beyond alert→report→dashboard):

detect → investigate → explain → assign → approve → execute → follow up → learn

2. Target Customers & Users

Customers: logistics, heavy-equipment rental, construction fleets, delivery, transportation, facility management, oil & gas, municipal, field service, and telematics service providers (resellers) — incl. companies on Wialon/Traccar/GPSWOX/Teltonika.

Users: Owner, Fleet Manager, Operations Manager, Dispatcher, Technical Support, Maintenance Manager, Fuel Analyst, Admin, Client Success, Reseller (manager), External Client (sub-user).

3. Product Principles

  • Map-first home; chat is core navigation; artifacts only when needed.
  • Action over visualization — what / why / who / next / approval / follow-up.
  • Backend (Django) is the source of truth.
  • No prompt-only security — RBAC, scoped tokens, allowlists, gateway, ClawPatrol, audit, approvals.
  • AI explains serious decisions (intent, tools, evidence, confidence, risk, approval, next, owner).
  • Strict customer isolation — zero cross-customer access.
  • Mine GPSWOX for knowledge, not code; keep Traccar as device engine.

8. Domain Knowledge Mined from GPSWOX

Rebuild clean in Python (mine via opensrc; do not port PHP).

8.1 Traccar linkage

Devices → protocol ports (tracker_ports) → Traccar decodes 44 protocols → positions + Redis live. devices.traccar_device_id → traccar_devices (key uniqueId = IMEI). Python: consume via REST(8082)+WS+Forwarding behind TraccarPort.

8.2 Position storage

GPSWOX shards across DBs (DatabaseService, user_database_pivot, table-per-device). Python: TimescaleDB hypertables (auto-partition/compression/retention), isolate by owner_id.

8.3 Sensors (~35) — most valuable

IgnitionEngineHoursOdometerFuelTankFuelConsumptionTemperatureRFIDSeatbeltBatteryDoorSatellitesGSMVINTachometerSpeedECMHarshAccelHarshBrakingHarshTurningLoadCounterLogicalNumericalTextual

Extraction logic = fuel-tank calibration, engine-hours from ACC, harsh thresholds. Python: SensorExtractor strategy per type, unit-tested.

8.4 Reports (~100)

Fuel (fillings/thefts/level/flow/tank-usage); drives/stops; geofences in/out; speed/overspeed/ECM; engine-hours/odometer; driver behavior (RAG/IVMS); general/travel-sheet/temperature; ops (offline/installation/sent-commands). Python: one Polars engine + ~10–15 core reports; rest on demand via Report Analyst.

8.5 Alerts & events

Alert + conditions → Event/EventLog. Types: geofence, overspeed, fuel drain/fill, ignition, offline, harsh, sensor, SOS, low battery. Python: AlertRule + rule engine on PositionReceived.

8.6 Commands (GPRS/SMS)

CommandTemplate, SentCommand, CommandSchedule; via Traccar/TCP or SMS. Python: TraccarPort.send_command() gated by ClawPatrol + approval.

12. Knowledge / RAG & Document Intelligence

Two truths: live operational (APIs/Traccar/DB) + knowledge/evidence (hybrid RAG). Unstructured (PDF/scan/screenshot/photo) → Surya OCR → chunk → embed → vector → grounded answer + citations. Curated (rules/specs/SOPs/exceptions) → OKF/MD navigated by agent. Both behind KnowledgePort; combine as GraphRAG. RAG types: Document, Image, Table, Case, Memory, Hybrid. Customer isolation + citations + logging mandatory.

Data Hub: connect → clean → structure → activate. Tables (manual/CSV/API/AI-filled/AI-analyzed), forms, surveys, quizzes, checklists, validation, sync jobs, automation triggers, agent access. Sources: telematics, business systems, comms, files.

Mini Apps: built from tables/forms/docs/automations/agents (wizard/prompt/from-table/from-doc). 15. Approval & Safety Model

  • Auto-approved (read-only): searches, history, summaries, drafts, allowed reads.
  • Confirmation: create geofence, send message, assign task, schedule automation, sensitive export, device settings, publish mini app, external share.
  • High-risk (ClawPatrol): delete, remove worker, disable device, change permissions, mass update, bulk commands, billing/security, public publish.
  • Flow: ask → prepare → RBAC → ClawPatrol → approval if risky → execute → audit.

20. Metrics · Risks · Final Principle

Metrics: time-to-asset/report, AI actions completed, approval completion, suggestion acceptance, doc-search success; reduced reporting time/unresolved alerts/offline/fuel anomalies/overdue maintenance; MRR, churn, adoption; safety: cross-customer incidents = zero, unauthorized retrieval = zero.

Top risks: scope breadth (prioritize the loop), AI trust (evidence+confidence+citations), messy data (connectors+mapping+CSV), dangerous automation (ClawPatrol+approvals+audit), Flue language split (isolated service + LiteLLM HTTP bridge).

Power + safety + domain focus + customer isolation + manager control + auditability. PutPath turns live telematics data, documents, tables, forms, workflows, and AI coworkers into safe, accountable, automated fleet operations — built on Traccar, rebuilt clean in Python, powered by Flue + LiteLLM + hybrid knowledge + TimesFM.
