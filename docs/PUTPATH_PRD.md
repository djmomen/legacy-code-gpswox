# 10. Product Principles

## 10.1 Map-First

The home page gives maximum space to the map.

Allowed by default:

* small vehicle labels
* geofence shapes
* route trails
* right floating tool rail
* top search
* bottom AI chat bar
* map zoom controls

Not allowed by default:

* large KPI cards covering the map
* noisy widgets
* always-open panels
* alerts blocking visibility
* dashboard clutter

The map is the operational surface.

## 10.2 Chat Is a Core Navigation Layer

Chat is not support.

Chat is how users operate PutPath.

Chat should:

* behave like ChatGPT
* support agent selection
* support conversation history
* support filters by agent
* support file attachments
* support artifacts
* create work requests
* request approvals
* generate reports
* open map context
* show tools/evidence when needed

## 10.3 Artifacts Appear Only When Needed

If the user needs a report, table, chart, map, timeline, compliance output, or structured investigation, PutPath opens an artifact canvas.

If not, the map stays visible.

## 10.4 AI Must Explain Serious Decisions

Every serious AI response should show:

* detected intent
* tools called
* data used
* evidence
* confidence score
* risk level
* approval status
* why suggested
* next action

## 10.5 Action Over Visualization

Dashboards are useful, but PutPath should push toward action.

Every major insight should answer:

* What happened?
* Why does it matter?
* Who owns it?
* What should happen next?
* Does it need approval?
* How will we follow up?

## 10.6 Backend Is the Source of Truth

AI agents do not own permissions.

PutPath backend owns:

* tenants
* users
* roles
* permissions
* approval rules
* data access
* business logic
* audit logs
* billing rules
* workflow state

## 10.7 No Prompt-Only Security

Prompts guide behavior.

Security must be enforced by:

* backend RBAC
* tenant-scoped tokens
* MCP/CLI tool allowlists
* permission gateway
* ClawPatrol runtime firewall
* audit logs
* human approvals

# 15. RAG Layer

## 15.1 Purpose

PutPath will include a dedicated **RAG layer**, meaning **Retrieval-Augmented Generation**.

RAG allows AI agents to answer from real company evidence instead of guessing.

The RAG layer retrieves relevant information first, then the LLM generates an answer grounded in that retrieved evidence.

PutPath will use RAG across:

* uploaded documents
* images
* scanned PDFs
* device manuals
* support screenshots
* maintenance forms
* contracts
* compliance documents
* previous reports
* customer records
* SOPs
* installation notes
* troubleshooting guides
* structured tables
* operational forms
* past cases
* company memory
* fleet rules
* client preferences

The rule:

```text
The AI must answer from evidence, not imagination.
```

## 15.2 RAG Role in PutPath

PutPath has two types of truth:

```text
1. Live operational truth
   Comes from APIs, Traccar, Wialon, GPSWOX, Teltonika, devices, sensors, and backend databases.

2. Knowledge and evidence truth
   Comes from RAG over documents, images, tables, manuals, forms, support records, previous cases, and company memory.
```

Clean formula:

```text
APIs = live operational truth
RAG = company knowledge and evidence
Hermes = reasoning and delegation
Django = business authority
ClawPatrol = risky-action firewall
React = user interface
```

## 15.3 RAG Pipeline

```text
Data source
  → ingestion
  → extraction
  → cleaning
  → chunking
  → metadata tagging
  → embedding
  → vector indexing
  → retrieval
  → reranking
  → grounding
  → LLM answer
  → citations
  → audit log
```

For documents and images:

```text
Upload PDF/image/screenshot
  → Surya OCR/layout/table extraction
  → extract text, tables, reading order, regions
  → chunk content
  → embed chunks
  → store vectors
  → store metadata in Django/PostgreSQL
  → retrieve relevant chunks
  → answer with citations
```

For structured tables:

```text
Upload table / connect source
  → map columns
  → validate data
  → clean duplicates
  → create dataset
  → expose dataset to agents
  → use in reports, automations, mini apps, and analysis
```

### Document RAG

Used for:

* PDFs
* manuals
* contracts
* reports


### Case RAG

Used for:

* previous investigations


### Memory RAG

Used for:


The agent checks:

* device manual
* past support cases

Then returns one grounded answer.

## 23.4 Approval Flow


# 29. Risks and Mitigation

## 29.1 Product Too Broad

Risk:

PutPath becomes too big and unfocused.

Mitigation:

Prioritize the core operational loop:

```text
data → AI judgment → case/work request → approval → execution → audit
```

## 29.2 AI Trust Risk

Risk:

Users do not trust AI.

Mitigation:

Show evidence, confidence, missing data, source files, citations, and approval requirements.

## 29.3 Integration Complexity

Risk:

Telematics data is messy.

Mitigation:

Start with stable connectors, flexible field mapping, CSV fallback, and strong data normalization.

## 29.4 Dangerous Automation

Risk:

AI performs wrong action.

Mitigation:

RBAC, approvals, ClawPatrol, audit logs, action limits, rollback where possible.

## 29.5 Competitors Add AI

Risk:

Large telematics platforms add AI.

Mitigation:

PutPath positions as cross-platform AI operating layer with responsibility graph, document intelligence, data hub, workflows, cases, memory, and human-approved execution.

## 29.6 Document Intelligence Accuracy

Risk:

OCR or retrieval gives weak answer.

Mitigation:

Show source citations, confidence, missing data, and never pretend uncertain evidence is final truth.

## 29.7 Data Hub Abuse

Risk:

Users create messy tables, unsafe automations, or expose sensitive data.

Mitigation:

Permissions, validation rules, approval gates, audit logs, row-level access, and external sharing controls.
