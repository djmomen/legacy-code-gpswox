② ربط Traccar — كيف يعمل فعليًا

GPSWOX لا يكلّم الأجهزة مباشرة — Traccar يفعل. الربط عبر ٤ قنوات (من config/tracker.php وtraccar_devices):

القناةالتفصيل (من الكود)
الإعدادGPSWOX يولّد إعداد Traccar: web.port=8082 (API)، database.url=jdbc:mysql…/gpswox_traccar، redis.enable=true، time.override=serverTime، registerUnknown=true (يسجّل المجهول تلقائيًا)
المنافذجدول tracker_ports = أي بروتوكول على أي منفذ (port/name/parent)؛ كل نوع جهاز له منفذ
ربط الجهازdevices.traccar_device_id → صف في traccar_devices (المفتاح uniqueId = IMEI)؛ traccar_devices يحمل آخر حالة: lat/lng/speed/course/power/protocol/latest_positions
اللحظيTraccar ينشر عبر Redis؛ GPSWOX يلتقط (PositionResultRetrievedListener) ويبثّ للواجهة

الربط في نسخة Python

نصيحة جوهرية: لا تقرأ جداول Traccar مباشرة (هشّ). استهلك Traccar عبر واجهاته الرسمية الثلاث، خلف TraccarPort واحد:

⑫ نصائح الترحيل PHP → Python

المجالالنصيحة
الاستراتيجيةعدّن المعرفة لا الكود. opensrc لقراءة منطق GPSWOX، ثم أعد بناءه نظيفًا — لا تترجم PHP سطرًا بسطر.
الأولويةPhase 1: Accounts + Tracking(عبر Traccar) + Geo + Alerting. كل الباقي لاحقًا.
Traccarلا تلمس محرّك البروتوكولات. استهلكه عبر API/WS/Forwarding فقط. هذا يوفّر سنوات عمل.
المواقعTimescaleDB بدل تقسيم MySQL اليدوي. owner_id للعزل.
المستشعراتأعِد بناء منطق الاستخلاص/المعايرة كـ strategies مختبَرة (هنا أثمن معرفة).
التقاريرمحرّك Polars واحد + AI agent، لا ١٠٠ تقرير مكتوب يدويًا.
الـ ORMتجنّب «fat models» الضخمة (User.php عملاق). domain نظيف + repositories.
الأمانانقل ConfirmedAction/OneSession/PermissionsHash؛ افرض owner_id في الـ service layer.
الأفعال الخطرةأوامر الأجهزة خلف ClawPatrol + موافقة + audit.
الديونتجاهل ٣٣٨ migration المتراكمة، الملفات .bak، والتقارير المخصّصة لعميل واحد (Birla/Automon…).
الخطوة العملية: أبدأ بـ opensrc path github:djmomen/legacy-code-gpswox ثم أعدّن سياقًا واحدًا (مثلًا المستشعرات + الوقود) وأحوّله إلى spec في Spec Kitty + ملفات OKF/MD معرفة. تريدني أبدأ بذلك؟
