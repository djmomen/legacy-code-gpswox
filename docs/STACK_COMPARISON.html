② جدول Scale — مقارنة بنود الـ Stack

البُعداتفاقناPRDالفائزلماذا (رأي هندسي)
تفكيك الخدمات Microservices كاملة مبكرًا Django مُمنهَج + workers (pragmatic) PRD Microservices مبكرة = ألم تشغيلي بلا عائد. نهج PRD البراغماتي أصحّ حتى تظهر أعراض scale حقيقية، ثم تُستخرج الخدمات تدريجيًا.
تخزين السلاسل الزمنية TimescaleDB للمواقع PostgreSQL عام اتفاقنا مواقع GPS = time-series ضخمة. TimescaleDB أفضل للاحتفاظ والاستعلام والـ downsampling — ويغذّي TimesFM للتنبؤ.
ناقل الأحداث Kafka غير محدّد بقوة اتفاقنا الحلقة الـ agentic event-driven تحتاج عمودًا فقريًا. ابدأ بـ Redis Streams وارتقِ لـ Kafka عند الحجم.
إطلاق الميزات / المراقبة Istio Service Mesh GrowthBook flags + observability PRD Istio ثقيل ولا يُبرّر إلا مع عشرات الخدمات. GrowthBook قيمته فورية (beta، A/B، إطفاء طارئ). Istio سابق لأوانه.
القراءة/الكتابة CQRS + Event Sourcing Read Models بسيطة عند الحاجة PRD Event Sourcing معقّد جدًا وبلا مبرّر قوي هنا. CQRS Read Models للتقارير الثقيلة كافٍ.
النسخ الاحتياطي / DR غير محدّد Databasus + WAL + backups سحابية PRD خطة DR ملموسة (نسخ، اختبار استرجاع، WAL).
توجيه النماذج عند الحجم LiteLLM Manifest اتفاقنا LiteLLM ينجز التوجيه + تتبع التكلفة + fallback بنضج أعلى؛ نضيف حدود العميل فوقه.

③ إضافة جديدة: TimesFM — طبقة التنبؤ

TimesFM (Google Research): نموذج تأسيسي للتنبؤ بالسلاسل الزمنية (200M معامل، مدرّب على 100 مليار نقطة، تنبؤ zero-shot، بايثون). يعمل كـ خدمة/worker تنبؤ تقرأ من TimescaleDB. استخداماته في PutPath: التنبؤ بالصيانة قبل الأعطال، توقّع استهلاك الوقود وكشف الشذوذ (متوقَّع مقابل فعلي)، تقدير الـ ETA، وتوقّع الاستخدام/الطلب — وقوده يصبّ في الـ AI agents (Fuel Investigator، Maintenance Watcher).
